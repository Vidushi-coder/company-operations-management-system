## Overview of Database Design

The system uses **MongoDB** as its database. MongoDB is a NoSQL document-oriented database where data is stored in flexible JSON-like documents rather than rigid table rows.

The database consists of **6 collections:**

- Users
- Employees
- Projects
- Tasks
- Leave Requests
- Notifications

### Why MongoDB

- It has a flexible document-oriented architecture which suits this project well since different modules store different shapes of data
- It can handle unstructured and semi-structured data efficiently without requiring a fixed schema
- It integrates naturally with Node.js and Mongoose ODM which are part of this project's tech stack
- It supports efficient aggregation queries, which the dashboard and analytics module relies on for chart data

## Collections

### Users Collection

The Users Collection stores login credentials and role information only. It does not store personal or professional employee details — those are stored separately in the Employees Collection.

**Note:** Users and Employees are intentionally kept as separate collections. A User represents a system account used for authentication. An Employee represents a person working at the organization. They are linked together but serve different purposes. Admin accounts, for example, are created directly and have no linked Employee record — this is intentional, not an oversight.

**Fields:**

- `_id` → unique identifier automatically generated by MongoDB for each user
- `name` → full name of the user
- `email` → used for login, must be unique across all users
- `password` → used for authentication, stored as a bcrypt hash and never as plain text
- `role` → defines access level, value is one of: Admin / Manager / Employee
- `createdAt` → timestamp of when the account was created

---

### Employees Collection

The Employees Collection stores the personal and professional details of every employee in the organization. Each employee record is linked to one User account through the `userId` field.

**Fields:**

- `userId` → references the `_id` of the corresponding User account for login (unique — enforces one-to-one)
- `name` → full name of the employee
- `email` → personal or work email used as contact information
- `phone` → contact phone number
- `department` → the department the employee belongs to (e.g. Engineering, HR, Finance)
- `designation` → job title or role of the employee (e.g. Software Engineer, Team Lead)
- `dateOfJoining` → the date on which the employee joined the organization
- `status` → current employment status, value is one of: Active / Inactive

---

### Projects Collection

The Projects Collection stores information about every project created within the organization. A project can have multiple employees assigned to it as members.

**Fields:**

- `title` → name of the project
- `description` → brief overview of what the project involves
- `status` → current state of the project, value is one of: Not Started / Active / On Hold / Completed
- `startDate` → the date on which the project officially begins
- `deadline` → the final date by which the project must be completed
- `createdBy` → references the `_id` of the Admin or Manager who created the project
- `members` → a list of employee IDs representing all employees assigned to this project

---

### Tasks Collection

The Tasks Collection stores individual tasks that are created under a specific project and assigned to a specific employee. Every task must belong to a project.

**Fields:**

- `title` → name of the task
- `description` → details of what needs to be done for this task
- `priority` → urgency level of the task, value is one of: High / Medium / Low
- `status` → current progress of the task, value is one of: To Do / In Progress / Done
- `projectId` → references the project this task belongs to, every task must be linked to a project
- `assignedTo` → references the employee ID of the person responsible for completing this task
- `createdBy` → references the `_id` of the Admin or Manager who created this task
- `dueDate` → the deadline for completing this specific task

---

### Leave Requests Collection

The Leave Requests Collection stores all leave applications submitted by employees along with their approval status and review details.

**Fields:**

- `employeeId` → references the employee who submitted this leave request
- `leaveType` → category of leave being requested, value is one of: Sick Leave / Casual Leave / Annual Leave
- `fromDate` → the starting date of the requested leave period
- `toDate` → the ending date of the requested leave period
- `reason` → explanation provided by the employee for requesting leave
- `status` → current state of the request, value is one of: Pending / Approved / Rejected
- `reviewedBy` → references the `_id` of the Admin or Manager who approved or rejected the request
- `appliedAt` → timestamp of when the leave request was submitted

---

### Notifications Collection

The Notifications Collection stores all system generated notifications triggered by key events such as leave submission, task assignments, project assignments, and leave request decisions. Each notification belongs to one specific user.

**Fields:**

- `userId` → references the user who should receive this notification
- `type` → category of notification: Task Assigned / Leave Approved / Leave Rejected / Project Assignment / Leave Requested
- `message` → the readable notification text shown to the user
- `isRead` → whether the user has read this notification: true / false
- `createdAt` → timestamp of when the notification was generated

---

## Relationships Between Collections

- Each **Employee** is linked to exactly one **User** account through `userId`
- Each **Task** belongs to exactly one **Project** through `projectId`
- Each **Task** is assigned to exactly one **Employee** through `assignedTo`
- Each **Project** can have many **Employees** through the `members` list
- Each **Leave Request** belongs to exactly one **Employee** through `employeeId`
- Each **Leave Request** is reviewed by one **User** (Admin or Manager) through `reviewedBy`
- Each **Project** and each **Task** is created by one **User** through `createdBy`
- Each **Notification** belongs to exactly one User through `userId`
- **Notifications** are automatically created when a Task is assigned, when a Leave Request is submitted (notifying Admins and Managers), when a Leave Request is reviewed (notifying the applicant), or when an Employee is added to a Project

## Data Flow Considerations — Resolved

These questions were raised during planning. Each is answered below based on the final implementation.

- **When a User account is deleted, what happens to their linked Employee record?**
  Resolved by design: there is no standalone "delete User" flow. Deletion is always initiated from the Employee side (`DELETE /api/employees/:id`), which cascades to delete the linked User account, all of that employee's Leave Requests, and all of their Notifications in one operation. Tasks assigned to that employee are unassigned (`assignedTo: null`), not deleted, so project history is preserved.

- **When an Employee is marked Inactive, should they still be able to log in?**
  Not currently enforced. `status: Inactive` is a display/HR field only — it does not disable the linked User account or block login. This is a known gap, documented as future scope (login should ideally be blocked when status is Inactive).

- **When a Project is deleted, what happens to its Tasks?**
  Not automatically cascaded. Tasks belonging to a deleted Project, and any Notifications referencing a deleted Task or Project, remain in the database (orphaned). This is a documented known limitation rather than an oversight — cleanup was deprioritized in favor of core feature completeness.

- **When an Employee is removed from a Project (but not deleted), what happens to Tasks assigned to them under that project?**
  Not automatically reassigned or unassigned. This differs from full employee deletion, where tasks are explicitly unassigned. Currently a manual cleanup step; noted as future scope.

- **When a Leave Request is pending and the employee's account is deactivated before review?**
  Not explicitly handled — no automatic cancellation logic exists. The request remains visible to Managers/Admins for review regardless of the employee's status.

- **Should the system prevent duplicate/overlapping Leave Requests?**
  Resolved: overlap detection is implemented. A new leave request is blocked if its date range overlaps with any existing **Pending** or **Approved** request for the same employee. Rejected requests do not block new applications for the same dates.

- **When a notification is read, should it be permanently stored or deleted after a period?**
  Resolved (partially): `isRead` flips to `true` on read; there is no automatic time-based deletion. Notifications persist until the user manually deletes them via `DELETE /api/notifications/:id`. Orphaned notifications for since-deleted tasks/projects also persist — see known limitations.

- **When a User is deleted, should their notifications be deleted too?**
  Resolved: yes, as part of the same cascading Employee-deletion operation described above — Notifications are deleted together with the User and Employee record.
